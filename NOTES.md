# Notes

## Key decisions

**Audit log shape: one row per changed field, not a JSON blob per event.**
`AuditLog` has `field` / `oldValue` / `newValue` columns rather than a single `changes: Json`
column holding an array. This makes the "field-level old -> new history" requirement a plain
`SELECT ... ORDER BY changedAt DESC` with no client-side unpacking, and keeps the audit-diff
unit tests (`backend/tests/auditDiff.test.ts`) trivial to assert against. The trade-off is a
few more rows per event instead of one - fine at this scale, and arguably clearer for an
audit trail an inspector needs to read.

**Diffing is a pure, dependency-free function (`src/lib/auditDiff.ts`).**
`diffFields(before, after, trackedFields)` only compares fields actually present in the
incoming payload, so a partial `PUT` (e.g. `{ status: "VERIFIED" }`) can never generate a
false diff for fields the caller didn't touch. Values are normalized (Date -> ISO string,
null/undefined -> null) before comparison so `cleanedAt` doesn't show a spurious change just
because Prisma returns a `Date` object and the payload has a string. `diffForCreate` seeds
the initial audit rows for a new record, skipping fields that were never populated.

**No-op updates don't write an audit entry.** If a `PUT` payload matches the current values
exactly, `updateCleaningRecordService` returns the existing record without touching the DB.
This keeps the audit trail meaningful (only real changes) instead of accumulating no-op
noise every time someone re-saves a form.

**Pagination: offset-based (`page`/`limit`), not keyset.** Simpler to implement and to
consume from the front-end (jump to any page, show total count), and cleaning records for a
single piece of equipment are not expected to reach a size where offset pagination's
performance cost matters. Keyset (cursor) pagination would be the better choice once a
table is large and insert-heavy (avoids the `OFFSET` scan cost and stays stable under
concurrent inserts), which could matter more for the audit log itself than for cleaning
records. Given the stretch-goal framing, I judged the extra complexity (opaque cursors,
losing "jump to page N" UX) wasn't worth it for this exercise.

**Equipment delete is blocked once it has cleaning records** (409 Conflict) - retiring
(`status: RETIRED`) is the supported way to decommission equipment that has history. In a
regulated environment you don't want a hard delete silently taking cleaning history with it.

**No real auth - a stand-in "current user".** The front-end has a "Current user" text
field (`ActorContext`, persisted to `localStorage`) sent as an `X-Actor` header; the API
middleware reads it (defaulting to `"Unknown User"`) and uses it as the audit log's
`changedBy`. `cleanedBy` is a separate, explicitly-entered field on the form - in practice
whoever *physically* cleaned the equipment isn't always the person entering the record.
This satisfies the "current user" stretch goal without building real auth, which felt out
of scope for a ~4-6 hour exercise.

**Server-side validation via Zod**, with a central error handler that turns `ZodError`,
custom `AppError`/`NotFoundError`/`ConflictError`, and known Prisma errors (unique
constraint, record-not-found) into consistent `{ error: { message, details? } }` responses
with correct status codes.

**Front-end has no router or data-fetching library.** With two screens (equipment list,
equipment detail) driven by a single piece of `App`-level state, adding React Router or
React Query would be pure ceremony. Each page/component fetches via a small typed
`fetch` wrapper (`src/api/client.ts`) and manages its own loading/error state with
`useState`/`useEffect`. This is the one place I'd reconsider first if the app grew (more
screens, deep-linkable URLs).

**Migration is hand-written to match `schema.prisma`**, rather than generated by running
`prisma migrate dev` against a live database (none was available while building this).
It's the SQL Prisma would generate for this schema; `prisma migrate deploy` applies it
as-is. If asked to explain any line of it, I can.

## How this was actually run and verified

This project was built and tested end-to-end against a free hosted Postgres instance
(Supabase), not a local install - the dev machine used to build this didn't have
PostgreSQL installed. Migrations, seeding, the API, the front-end, and all tests were run
and confirmed working against the real hosted database.

Docker/docker-compose was deliberately left out (it's an optional stretch goal, and
Docker wasn't installed on the dev machine either) rather than shipping an untested
Dockerfile and compose file.

## Assumptions (per the "note it and keep going" instruction)

- `cleanedBy` is free text, not a foreign key to a user table - there's no user/auth model
  in the brief, and inventing one felt like over-building.
- `cleanedAt` from the front-end's `<input type="datetime-local">` is interpreted as the
  browser's local time and stored as a UTC timestamp; there's no explicit timezone/site
  handling. Fine for a single-site demo; would need revisiting for a multi-site deployment.
- Equipment list is not paginated (the brief only requires pagination on cleaning records);
  it's a simple filtered list.

## What I'd do differently with more time

- Real authentication (even a simple JWT + user table) instead of the `X-Actor` stub, so
  `changedBy` can't be spoofed by the client.
- Optimistic concurrency control on `CleaningRecord` updates (an `updatedAt`/version check)
  so two people editing the same record don't silently overwrite each other - currently
  last write wins.
- Keyset pagination for the audit log specifically, since it's the table most likely to
  grow large and append-only over an equipment's lifetime.
- Deep-linkable URLs (React Router) once there's more than two screens.
- End-to-end tests (Playwright) covering the full create -> edit -> view-audit flow through
  the real UI; what's here is unit/service tests on the backend and component tests on the
  front-end.
- A CI workflow (lint + typecheck + test) - not included since there's no CI runner to
  wire it to for this exercise.

## What I deliberately left out

- Soft-delete/undo for cleaning records - not requested, and would need its own audit
  semantics ("deleted" vs "updated") that the brief doesn't specify.
- Bulk operations (bulk verify, CSV export) - out of scope for the core requirements.
- Rate limiting / request logging middleware - reasonable for production, not needed to
  demonstrate the exercise's requirements.
